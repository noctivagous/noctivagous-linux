Noctivagous Linux — Foundation

The source tree of the real system: what is built first, how it is organised, and the chain it has to prove before anything else is added.

The chain

The foundation exists to make one sequence work, end to end, with a basic setup. Everything else in the desktop is built on top of this sequence once it holds.

1 · Bootgreetd starts the greeter session
→
2 · GreeterThe Godot greeter runs fullscreen
→
3 · LoginCredentials checked through the auth bridge
→
4 · SessionThe compositor starts; the shell comes up
→
5 · LaunchPre-set programs open from inside the session

The programs in step 5 are set up in advance, in one list (core/session/launch-list.tsv), and cover the three kinds of citizen the desktop has to host from the first day:

  • A foreign browser — Firefox.
  • A foreign toolkit app — a Qt program (QTerminal in the foundation setup).
  • One of our own apps — a Godot application on the pinned runtime (nct-hello in the foundation setup).

Three different kinds of work

The system is three kinds of work with three different build-and-test loops. They are kept in separate parts of the tree so they never blur into each other.

KindWhere it livesWhat it isHow it is tested
Coresrc/core/ A wlroots-class compositor (a stand-in compositor in the foundation), seat and session glue, the session scripts. On real DRM and seat hardware — in the virtual machine.
Godot system layersrc/godot/ The greeter, the shell, the kit and the apps: GDScript and scenes on one pinned engine runtime, with native extensions where the system needs reach beyond the engine. Headless and in a nested Wayland session — most of it never needs the virtual machine.
Distro plumbingsrc/distro/, src/system/ The Debian base: package lists, and an overlay that mirrors the installed filesystem path for path. By booting the installed image in the virtual machine.

Foreign programs are not a fourth kind of work in the tree. A foreign app is a surface the compositor hosts; its own source never lives here. Only its bundle and registration — if it takes them — are recorded, under the external-frameworks rules (src/ext-fwks/).

The hosting rule. A compositor feature may depend only on surface-level facts — geometry, state, focus, stacking — never on the native kit contract. That is what lets the same desktop host Firefox, a Qt app, and a Godot app without knowing anything about what is inside them.

How the pieces of the chain fit

Greeter and login

greetd starts a single-app session: a small compositor (cage) running the Godot greeter fullscreen. Godot has no Unix-socket API, so the greeter cannot speak greetd's protocol directly. A small bridge service does: greetd's IPC on one side, a one-line local protocol on the other, which the greeter uses to offer credentials and, on success, to start the session. In tests without greetd, the same bridge checks a fixture account, so the greeter and the protocol are exercised identically.

Session and shell

The session script starts the compositor; the compositor's autostart starts the shell and then every launch-list entry marked for autostart. The shell is a separate Godot process from the greeter and from every app, so a shell failure is a restart, not a lost session.

Launching

The shell's buttons and the autostart use the same launcher script and the same list. A program is added to the desktop by adding a line to the list — its name, its command, whether it autostarts — not by editing the shell.

Test tiers

TierWhereWhat it establishes
0 — HeadlessAny machine Projects import and validate, scripts parse, the bridge answers, the launcher resolves every list entry.
1 — NestedAny machine with wlroots The whole chain inside a headless compositor: greeter, login, session apps, all three citizens open — checked against the window tree and screenshots.
2 — VMThe Windows box, VirtualBox Boot, greetd, the seat, and the chain on virtual GPU hardware. The test bed in tests/vm/ runs the checks and leaves logs and screenshots for whatever fails.

The test rig

Development happens in Muse; the tier-2 proof happens on a spare Windows machine. VirtualBox is defined by one text file (a Vagrantfile), provisioned by one script, and controlled from the terminal — VBoxManage for the machine, SSH (forwarded to the host's port 2222) for everything inside it. Muse Code on that machine pulls the repository, brings the VM up, runs the test bed, and works from its results. The guest is disposable; the repository is the record. Details and the running log live in VM-RIG.md.

Foundation run, 2026-11-25. The desktop environment itself is still being designed in demo-de; this tree is the ground it will stand on, built chain-first.
